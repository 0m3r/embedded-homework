# ESP32-S3 — дослідження debounce

Перші чотири частини домашньої роботи працюють паралельно в одній прошивці.

| Лог | Завдання | Метод |
| --- | --- | --- |
| `No debounce` | 1 | interrupt `FALLING`, без debounce |
| `Time-based` | 2 | 50 мс між прийнятими подіями, обробка поза ISR |
| `State-based` | 3 | подія ISR + перевірка рівня через 50 мс |
| `Polling` | 4 | polling кожні 5 мс, машина станів |

ISR лише збільшує лічильник подій. Логування та debounce виконуються в
`loop()`, не в interrupt context.

## Архітектура

- `Application` читає одну фізичну кнопку та передає однакові дані всім методам;
- `Button` володіє GPIO interrupt і лічильником сирих подій;
- `NoDebounceCounter`, `TimeBasedDebouncer`, `StateBasedDebouncer` та
  `PollingDebouncer` лежать у папці `Debouncer` та реалізують спільний
  C++-інтерфейс `IDebouncer`;
- `Logger` централізує весь Serial-вивід;
- `Config` зберігає піни та часові параметри.

Використовується одна кнопка, щоб усі методи отримували той самий фізичний
сигнал. Різні кнопки мали б різний брязкіт і спотворили порівняння.

## Підключення без RC

```text
3.3V --- 10 kOhm ---+--- GPIO21
                    |
                  button
                    |
                   GND
```

## Підключення з hardware RC

```text
3.3V --- 10 kOhm ---+--- GPIO21
                    |
                    +--- 100 nF --- GND
                    |
                    +--- button --- 220 Ohm --- GND
```

За умовою потрібен `100 Ом`; у фізичному тесті використано доступний
`220 Ом`. GPIO налаштований як `INPUT`, підтяжка — зовнішня `10 кОм`.

## Збірка і прошивання

```bash
pio run -t upload
pio device monitor -b 115200
```

Нічого перемикати не потрібно. Одне фізичне натискання обробляють усі чотири
алгоритми, кожен веде власний лічильник.

## Результати

Тести виконані на одній фізичній кнопці. Кількість хибних спрацювань — різниця
між лічильником методу та реальною кількістю натискань.

### Без RC — 17 натискань

| Метод | Подій | Хибних |
| --- | ---: | ---: |
| Без debounce | 83 | 66 |
| Time-based | 29 | 12 |
| State-based | 17 | 0 |
| Polling | 17 | 0 |

### Hardware RC — 10 натискань

| Метод | Подій | Хибних |
| --- | ---: | ---: |
| Без debounce | 101 | 91 |
| Time-based | 20 | 10 |
| State-based | 10 | 0 |
| Polling | 10 | 0 |

## Порівняння

| Метод | Хибні спрацювання | Затримка | Складність | Коментар |
| --- | --- | --- | --- | --- |
| Без debounce | дуже багато | мінімальна | низька | один натиск створює багато interrupt |
| Time-based | менше, але залишились | до 50 мс lockout | низька | можливі події під час відпускання |
| State-based | 0 | приблизно 50 мс | середня | стабільні press і release |
| Polling | 0 | 50–55 мс | середня | найстабільніша поведінка |
| Hardware RC | не усунув bounce | приблизно 1 мс RC | середня | `10 кОм × 100 нФ` недостатньо для цієї кнопки |

## Висновки

- ISR має лише фіксувати подію; Serial-вивід і debounce виконуються в loop.
- Простий time-based фільтр суттєво зменшує bounce, але не гарантує одну подію.
- State-based і polling дали рівно одну реакцію на кожне натискання.
- RC із заданими `10 кОм` і `100 нФ` має сталу часу близько `1 мс`. У цьому
  макеті він не покращив raw interrupt: повільний фронт біля цифрового порога
  створював додаткові `FALLING` події.
- Для чесного порівняння всі алгоритми паралельно обробляли ту саму кнопку.
